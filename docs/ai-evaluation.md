# AI evaluation

> Status: the evaluation harness, golden dataset (32 cases) and CI regression gate are implemented.
> The deterministic **heuristic baseline has been measured** (results in §8). **No live-model
> results exist**: no API key was available while building, so model accuracy, latency and cost are
> *not yet measured*.

## 1. What the AI does — and does not do

The model performs exactly one task: **given an advisory (and, when available, the upstream fix
diff), propose the functions/methods/classes in the affected package that contain the vulnerable
behaviour.**

It does not decide reachability, severity, risk, or VEX status. Its proposals are inputs to a
deterministic verifier; only verified symbols are used by the reachability engine
([ADR-0008](decisions/0008-ai-proposes-deterministic-decides.md)).

## 2. Pipeline under evaluation

```
input builder ─▶ provider ─▶ parse (JSON schema) ─▶ normalise names ─▶ verify in source ─▶ diff cross-check ─▶ accepted set
```

Evaluation scores **two** outputs, because they answer different questions:

- **Raw model output** — how good is the model/prompt? (prompt and model selection)
- **Accepted set after verification** — what does the product actually use? (product quality)

The difference between the two is the guardrails' contribution, and is reported explicitly.

## 3. Golden dataset

Location: `backend/tests/ai/golden/cases/` — one JSON file per case: the advisory (id, summary,
details, references), the package and vulnerable version, the recorded upstream fix diff when one
exists, and three labelled symbol sets.

```json
{
  "id": "pyyaml-ghsa-8q59-q68h-6hv4",
  "advisory": {"id": "GHSA-8q59-q68h-6hv4", "summary": "…", "details": "…", "references": ["…"]},
  "package": {"name": "pyyaml", "vulnerable_version": "5.3"},
  "fix_diff": "diff --git a/lib/yaml/constructor.py …",
  "expected": ["yaml.load", "yaml.full_load", "yaml.load_all", "yaml.full_load_all", "yaml.FullLoader"],
  "acceptable": [],
  "unacceptable": ["yaml.safe_load", "yaml.safe_dump"],
  "label_source": "curated: FullLoader can construct arbitrary Python objects; the 5.4 fix restricted FullConstructor.",
  "tags": ["has_fix_diff"]
}
```

Current composition (2026-10-06):

| | Cases |
|---|---|
| Total | 32 |
| With a recorded fix diff / without | 30 / 2 |
| Adversarial (advisory text carries a prompt-injection string naming a decoy symbol) | 6 |
| Packages | requests 8, jinja2 6, pyyaml 4, urllib3 4, werkzeug 4, certifi 2, flask 2, idna 1, pyjwt 1 |

How the labels were made, stated plainly: the expected symbols are the same hand-curated entries
the demo uses (`backend/src/sieve/symbols/curated.json`), written during development from each
advisory's text and its upstream fix commit, and each verified to exist in the package source.
They have **not** been reviewed by a second, independent person. Labels are never generated by the
model under test.

The dataset is below the 50-case target set in the original plan, and 32 cases is enough to catch
regressions, not to make general accuracy claims about any model.

## 4. Metrics

For each case, `E` = expected ∪ acceptable, `P` = proposed set.

| Metric | Definition |
|---|---|
| Precision | `|P ∩ E| / |P|` (micro-averaged over cases) |
| Recall | `|P ∩ expected| / |expected|` — acceptable alternatives do not inflate recall |
| Hallucination rate | share of proposed symbols that **do not exist** in the package source at the vulnerable version |
| Unacceptable-hit rate | share of cases whose accepted set contains an `unacceptable` symbol |
| Structured-output failure rate | share of calls whose output failed schema validation |
| Latency | p50 wall-clock per call |
| Tokens | input / output tokens per call (provider-reported) |
| Cost | estimated USD per run, from the price table in `sieve/ai/providers.py` |

Every metric is reported twice: for the **raw** proposals and for the **accepted** set after
verification. The difference is what the guardrails contribute.

## 5. Running

```
make ai-eval                       # heuristic provider, compared against the committed baseline
cd backend && uv run python -m sieve.ai.evaluation --provider anthropic --model claude-opus-5-5     --out ../reports/ai-eval/anthropic          # live; reads ANTHROPIC_API_KEY
```

Both modes run the full pipeline: prompt building, the provider, schema parsing, name
normalisation, verification against the real package source (downloaded from PyPI and cached),
fix-diff cross-check, and metrics. The heuristic provider makes no network call to a model, so the
CI run is deterministic. There is no record/replay of live model responses yet; a live run calls
the model every time.

## 6. Regression gate

Every run writes `report.json` and `report.md`. With `--baseline`, the run fails if:

- accepted-set precision or recall falls by more than 0.02 below the baseline, or
- any non-existent symbol reaches the accepted set (the target is zero, and it is enforceable
  because verification is deterministic), or
- more cases accept a known-wrong (`unacceptable`) symbol than in the baseline.

CI runs the heuristic provider against `backend/tests/ai/golden/baseline-heuristic.json` on every
pull request, so a change that weakens verification, normalisation or diff matching fails even
though no model is called. Changing the baseline means committing the new report in the same pull
request.

## 7. Prompt versioning

The prompt is `backend/src/sieve/ai/prompts/symbol_extraction_v1.md`; its version string
(`symbol-extraction/v1`) is part of the extraction cache key and is recorded on every extraction
row, so a prompt change never serves stale cached results.

## 8. Results

### Heuristic baseline — 2026-10-06

Provider `diff-heuristic-v1` (deterministic: proposes every function the fix diff changes, named by
its module), prompt `symbol-extraction/v1`, 32 cases. Full per-case table:
[`reports/ai-eval/heuristic/report.md`](../reports/ai-eval/heuristic/report.md).

| Metric | Raw proposals | Accepted after verification |
|---|---|---|
| Precision | 17.0% | 44.1% |
| Recall | 31.2% | 31.2% |
| Proposed symbols that do not exist in the source | 58.7% | **0** reached the accepted set |
| Cases accepting a known-wrong symbol | — | 0.0% (including all 6 adversarial cases) |

What this shows: verification lifts precision from 17% to 44% without losing recall, and nothing
that does not exist in the package survives. What it does not show: how well a language model
does. The heuristic finds the right symbol in under a third of cases, which is why findings without
verified symbols become `needs_review`, never `not_reached`.
